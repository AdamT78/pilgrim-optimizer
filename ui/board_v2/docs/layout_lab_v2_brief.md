# Duty Wheel Layout Lab — V2 brief

Kept verbatim, for the same reason as the first brief: it records what was asked for, and
what was explicitly left to judgement. Where a decision was left open, the choice made and
the reason for it are written down in `layout_lab/README.md` under *Decisions the brief left
open*.

---

Please update the existing **Duty Wheel Layout Lab** to a V2.

IMPORTANT:
- Work from the existing implementation.
- Preserve all currently working functionality unless a change below explicitly supersedes it.
- Do not rewrite the tool from scratch unless technically necessary.
- Keep the fixed internal design coordinate system at exactly **1200 × 1200 px**.
- The purpose remains a spatial/layout prototyping tool, not the final game UI.
- Keep the implementation local/offline, with no framework or network dependency.
- Continue using the existing plain HTML/CSS/vanilla JavaScript approach generated by the Python script.

The V2 changes are listed below in priority order.

## 1. Two separate action-art objects per duty

Each of the eight Duties has TWO separate action options and therefore needs TWO independently
editable scenic-art objects.

The eight Duties remain: Allocation, Build Roads, Clerical, Construct, Give Alms, Ordination,
Produce, Taxation.

Currently each Duty has a single scenic-art object. Replace this with:

```
Duty
  ├── actionA
  │    └── art
  ├── actionB
  │    └── art
  ├── label
  └── figures
```

For example, Clerical may eventually use Action A: Gain Piety, Action B: Gain Coins.

The layout tool does NOT need to understand the gameplay meaning of the actions yet. It only
needs to support two independently positioned pieces of artwork.

Each action-art object must independently support: X, Y, width, height, opacity, visibility,
lock/unlock, image load, image clear, contain/cover, z-order, Send Backward, Bring Forward,
put behind / in front of wheel, horizontal mirror, vertical mirror, reset.

Give them useful editor names such as `Clerical · Action A`, `Clerical · Action B`,
`Allocation · Action A`, `Allocation · Action B`.

The two artwork objects for a Duty should NOT be forced to have the same size. Start with
sensible placeholder boxes, but expect them to be individually adjusted.

### Optional group movement

Add a useful way to move both action artworks of one Duty together once their internal
relationship has been established — select Duty group and drag both, or a
`Move Action A + B Together` button.

Do NOT permanently bind the two pieces together. I still need to be able to edit each one
independently.

### Data model

```
duties: {
  clerical: {
    name: "Clerical",
    actionA: { art: { x, y, width, height, opacity, fit, z, locked, visible, image, imageName } },
    actionB: { art: { ... } },
    label: {...},
    figures: {...}
  }
}
```

Migration from existing saved V1 state should be graceful if practical. If an old state contains
only one Duty art object, import it as Action A and initialize Action B from defaults.

## 2. Realistic-size / adjustable acolytes

The existing placeholder figures are much too small for meaningful layout evaluation. The tool
must now let me test figures at sizes comparable to the actual game miniatures.

### Size

Add a global control `Acolyte Height`, range **90 px to 210 px**, slider AND numeric input,
default approximately **120 px**. The chosen value represents the approximate on-screen height
of the acolyte figure in the 1200 × 1200 design coordinate system. All Duty acolyte placeholders
should update immediately when this value changes.

The City and In-Hand displays may optionally use independent scaling percentages relative to
this global size if needed — for example Duty figures 100%, City representative figure 75%,
In-Hand representative figure 85%. Expose these ratios if useful, but keep the UI simple.

### Acolyte visual mode

Add a prominent global selector `Acolyte Style: Painted | Colored`.

**COLORED** represents game pieces that are primarily identified by player colour. If no real
asset is loaded, use a good simplified miniature silhouette placeholder. Each of four players
should still have an editable player colour. The colored placeholder should visually resemble a
board-game miniature more than a generic circle.

**PAINTED** represents a fully painted miniature / character image. Allow transparent PNG/WebP
images to be loaded for painted acolytes. Ideally allow one painted acolyte asset per player.
If only one painted asset is provided, allow it to be reused for all players for layout testing.
Also allow optional Colored-mode image assets if straightforward. If no image asset has been
loaded, fall back to the generated placeholder.

Images must preserve aspect ratio, have transparent background support, scale according to the
Acolyte Height control, and remain anchored properly when changing size.

### Duty occupancy

Continue supporting occupancy counts 0–4 per Duty. The important test is whether FOUR
realistically sized acolytes can occupy a Duty space without making the wheel/art unreadable.

Keep or improve spacing control and compact arrangement mode. Also add, if practical:
horizontal row, compact/staggered, shallow arc. Do not make this unnecessarily complex.

### Player colors

Allow each individual displayed Duty acolyte to optionally use one of the four player
identities. At minimum, allow a Duty group to choose all Player 1 … all Player 4. If
straightforward, allow a mixed group of up to four player assignments, because eventually
multiple players may occupy the same Duty — preferable for testing majority readability.

## 3. Attach functional elements to the wheel

Currently the wheel can move/resize independently while Duty figure anchors and the In-Hand
object remain at absolute stage positions. Improve this.

The following should optionally be **wheel-relative**: the eight Duty figure anchors, the centre
In-Hand display, and optionally the Duty labels.

Do NOT automatically attach the scenic Action A / Action B artwork. Do NOT automatically attach
the City.

### Normalized coordinates

Use normalized coordinates relative to the wheel where practical — `u = 0.50`, `v = 0.12` rather
than only absolute `x = 600`, `y = 375`. A wheel-relative object's screen/design position should
be calculated from `wheel.x`, `wheel.y`, `wheel.width`, `wheel.height`, `u`, `v`.

When the wheel moves or scales, Duty figure anchors move with it, the In-Hand centre moves with
it, and attached Duty labels move with it. Their relative positions should stay correct.

### Control

Add a global toggle such as `Attach functional elements to wheel`, default ON. Also allow
individual Duty labels to detach if practical. When detached, preserve their current absolute
position. When attached, calculate and preserve their relative position.

The scenic action artwork must remain free-floating because I specifically want to experiment
with how much it overlaps the wheel. The City must remain independently movable.

## 4. Pure black preview background

Change the default stage background to `#000000`. This is important because the generated scenic
artwork is designed to fade into black.

Add a small background selector `Preview Background` with options Black (`#000000`) and Game Dark
(the existing dark brown/black background currently used by the lab). Default to Black.

The selected background should affect both Edit Mode and Clean Preview. Do not export editor
chrome.

## 5. Undo / redo

Add proper Undo / Redo. Controls: Undo, Redo. Keyboard: Ctrl+Z / Cmd+Z = Undo,
Ctrl+Shift+Z / Cmd+Shift+Z = Redo. Store approximately the last 30–50 meaningful states.

Do NOT push hundreds of history entries while one drag gesture is occurring. Preferred behavior:
pointer down → drag continuously → pointer up → ONE history entry. Likewise, slider drag may be
consolidated where practical.

Undo/Redo should include layout/state changes such as move, resize, visibility, opacity, art
image assignment, figure size, occupancy, City changes, In-Hand changes, wheel scaling,
background selection.

Do not add editor-only transient selection changes to undo history.

## 6. Change autosave so large images do not fill localStorage

The current implementation stores the entire state including embedded data-URL images in
localStorage. Change this. Automatic browser persistence should store **geometry/settings only**.
Do NOT automatically put large image data URLs into localStorage.

The geometry-only autosave should remember positions, dimensions, opacity, visibility, z-order,
locks, counts, figure size, player colours, image filenames / references if useful, and editor
settings — but not the actual image binary/data URL.

If image assets are lost after browser refresh, display a clear placeholder saying something such
as `Reload: clerical_piety.png` rather than silently pretending the image is still loaded.

Do NOT implement IndexedDB unless clearly useful and clean. A geometry-only localStorage
implementation is sufficient for now.

## 7. Separate "Lab Session" from "Game Layout" export

### A. Save / export Lab Session

This is for reopening the prototype. It may contain all geometry, all editor state, guide state,
mode, occupancy test counts, player colours, action images, optional embedded image data,
background selection, zoom, and all prototype-specific state.

Provide `Export Lab Session`, allowing me to choose whether images are embedded. Also provide
`Import Lab Session`.

### B. Copy / export Game Layout

This is production-oriented data intended to be consumed later by the real game UI. Create
`Copy Game Layout` and preferably `Export Game Layout JSON`. This should exclude editor/debug
state.

A production-oriented schema should resemble:

```
{
  "version": 2,
  "canvas": { "width": 1200, "height": 1200 },
  "wheel": { "x": ..., "y": ..., "width": ..., "height": ... },
  "duties": {
    "clerical": {
      "actionA": { "x": ..., "y": ..., "width": ..., "height": ..., "z": ... },
      "actionB": { "x": ..., "y": ..., "width": ..., "height": ..., "z": ... },
      "label": {...},
      "figures": { "u": ..., "v": ..., "spacing": ..., "arrangement": ... }
    }
  },
  "city": { "x": ..., "y": ..., "width": ..., "height": ... },
  "inHand": { "u": ..., "v": ..., "width": ..., "height": ... },
  "acolytes": { "height": ... }
}
```

Do NOT include things such as 50 px guide visibility, current editor selection, Edit/Clean mode,
undo history, zoom UI state, or temporary status messages. Keep this schema readable and stable.

## 8. Add zoom controls

The existing automatic FIT behavior should remain. Add FIT, 50%, 75%, 100%, 125%, and if useful
150%.

The stage must still retain a true 1200 × 1200 internal coordinate system. Zoom is display-only.
At 100%, 1 design pixel = 1 CSS pixel. If the zoomed stage is larger than the available
workspace, allow the stage workspace to scroll. Do not distort the stage. Do not let zoom alter
saved object geometry. Display the active zoom clearly. A mouse-wheel zoom modifier is optional
and not required.

## 9. Optional City background image

Keep the current City concept: a separate reserve outside the wheel, preferably below it, one
representative acolyte + count per player, not a ninth Duty, not a merchant destination, no Duty
action, no tithe resource.

Add an optional image slot for the City background, allowing PNG, JPG, WebP, and SVG if easy. The
City background image should support contain, cover, opacity, and clear image.

The City region remains independently movable, resizable, lockable, and visible/hidden. The
representative player acolytes and counts render on top of the City artwork.

Do NOT require City artwork. The existing generic placeholder remains the fallback.

## 10. Module-boundary warnings

Keep the ability to move objects partially outside the 1200 × 1200 stage. Do NOT hard-clamp every
layout object to the stage. Instead add visual warnings in Edit Mode.

If an object extends beyond the module boundary, indicate it clearly — for example
`OUTSIDE MODULE right +27 px`, or `left -18 / bottom +42`. A subtle red editing outline / warning
badge is sufficient.

Warnings should apply to relevant visible objects such as Action A/B artwork, the City, labels,
and figures where meaningful.

Do not show these warnings in Clean Preview. Do not include warnings in PNG/game-layout exports.

## Additional cleanup

### A. SVG wheel aspect ratio

The wheel asset is an SVG that will already have the correct 32° appearance. When loading SVG:
parse the SVG text, inspect the `viewBox`, derive `ratio = viewBoxHeight / viewBoxWidth`, and use
that as the authoritative natural aspect ratio. Fall back to browser
naturalWidth/naturalHeight only if no valid viewBox is available. The wheel must never be
non-uniformly scaled.

### B. Wheel reset

Resetting the wheel must not accidentally force it back to a mathematically derived sin(32°)
ratio if an imported SVG has its own valid aspect ratio. If an asset is currently loaded,
preserve the loaded asset's intrinsic ratio.

### C. Clean Preview

Clean Preview should hide bounding boxes, resize handles, names, anchor markers, boundary
warnings, grid, safe area, guides, and selection outlines. It should retain the wheel,
Action A/B artwork, Duty labels, acolytes, City, City counts, In-Hand display, and the chosen
stage background.

### D. Full-screen mode

Keep the existing full-screen behavior. It should work correctly together with FIT, manual zoom,
scrolling, and Clean Preview.

## Do not add yet

Do not expand this into the rest of the game. No player boards, resource tracks elsewhere,
merchant interface elsewhere, complete 2039 × 1200 board, complete 2283 × 1200 board, final
gameplay logic, final action buttons, or final animation system.

The purpose of the tool remains: can the Duty Wheel, 16 action artworks, realistically sized
acolytes, the City and the In-Hand display fit clearly and attractively inside ONE fixed
1200 × 1200 module?

## Updated default test state

Create a useful crowded default/test configuration. Suggested:

- Wheel: ~780 px wide, centered horizontally, slightly above vertical center
- Acolyte Height: 120 px
- Acolyte Style: Colored
- Duty occupancy: Clerical 4, Allocation 3, Build Roads 2, Ordination 1, Give Alms 4,

This intentionally represents a busy board state.
