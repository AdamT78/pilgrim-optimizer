# Layout Lab — the brief

This is the brief `layout_lab/` was built from, kept verbatim because it records what was
asked for. Where it left something to judgement, the choice made is recorded in
`layout_lab/README.md` under "Decisions the brief left open" rather than here, so this file
stays what it was rather than becoming a changelog.

---

Build a small local prototyping tool for a board-game UI called the **Duty Wheel Layout Lab**.

I want the tool to be generated by a script and opened as a standalone HTML page in a browser.

Use a simple implementation with no framework dependency unless there is a compelling reason. Prefer:

- Python 3 script to generate the HTML
- plain HTML
- CSS
- vanilla JavaScript
- no build system
- no server required
- no React/Vue/Svelte
- no external CDN dependencies
- no network access required

The purpose is **not** to build the final game UI. It is a layout lab where I can place and size the Duty Wheel, its surrounding scenic artwork, the City reserve, and the temporary "acolytes in hand" display, then record exact coordinates.

## Fixed design coordinate system

The canvas represents a fixed **1200 × 1200 px** Duty Wheel module.

This is an internal design coordinate system. The browser may scale the visual stage down to fit the available window, but:

- all X/Y/width/height values must remain in true 1200 × 1200 coordinates,
- mouse dragging and resizing must correctly translate between displayed scale and design coordinates,
- exported layout data must use the true 1200 × 1200 coordinates.

The module will eventually be placed unchanged inside either:

- 2039 × 1200 full-game canvas
- 2283 × 1200 full-game canvas

## Game-layout concept

The Duty Wheel has exactly eight Duty spaces: Allocation, Build Roads, Clerical, Construct,
Give Alms, Ordination, Produce, Taxation.

The **City is not a ninth Duty**. It has no Duty action, no tithe resource, no merchant, and
potentially many more acolytes than normal Duty spaces. It is represented as a separate
reserve below the wheel.

The centre of the wheel is used temporarily to show acolytes currently "in hand" while sowing.

## Wheel asset

The wheel SVG comes later and will already have the intended **32° elevated appearance**. The
tool must NOT squash, stretch, or independently re-project it: load a local SVG by file input,
move it, scale it uniformly, set opacity, lock it, reset it, and preserve aspect ratio at all
times. Until one is loaded, show a neutral placeholder about **780 px** wide.

## Eight scenic Duty-art regions

One editable region per Duty: draggable, independently resizable, numeric X/Y/width/height,
opacity, a visible name in Edit Mode, loadable local PNG/JPG/WebP/SVG, `contain` and `cover`
fit modes, z-order relative to the wheel, lock/unlock, reset. Start around **220 × 180 px**
each with independent sizes. They may overlap behind the wheel. The box border is an editing
aid, not a design element.

## Default layout

Eight regions arranged around the wheel at roughly 12, 1:30, 3, 4:30, 6, 7:30, 9 and 10:30
o'clock, with enough lower space left for the City reserve.

## City reserve

A separate editable region, initially centred below the wheel, roughly **260 px** wide:
draggable, resizable, exact geometry, lock/unlock, Edit Mode bounding box. Inside it, four
optional player placeholders, each one representative figure marker plus a count such as `×5`,
with show/hide, count 0–99, label and a prototype colour. The City always uses one
representative figure plus a count, even when the count is 1.

## In-hand / sowing display

A temporary region in the centre of the wheel, default around **150 px**: Edit Mode box,
draggable, resizable, exact geometry, show/hide, one representative figure plus a prominent
remaining count 0–99, text mode `×6` or `6 LEFT`, and a prototype colour. When hidden, the
centre shows a neutral decorative medallion so the idle composition can be judged. Never
render every in-hand acolyte individually.

## Figure occupancy simulator for Duties

Per Duty, choose 0–4 placeholder acolytes, drawn on or near the wheel rather than in the
scenic art. Because the imported SVG's duty geometry may differ, each Duty's figure-group
anchor is itself draggable. Store per Duty: anchor X/Y, occupancy count, spacing, and a
compact arrangement mode if easy.

## Duty label placeholders

Lightweight placeholders for the eight names: draggable, numeric X/Y, show/hide, a width or
scale setting. Plus a separate City label managed independently.

## Edit Mode vs Clean Preview

A prominent toggle. Edit Mode shows bounding boxes, handles, names, guides, selection outlines
and the numeric editor. Clean Preview shows only wheel, scenic images, labels, simulated
acolytes, City, City counts and the in-hand display.

## Guides

Toggles for stage boundary, horizontal and vertical centre lines, a 50 px grid, a safe area
about 50 px from each edge, and a wheel centre marker. Guides must not appear in Clean Preview.

## Selection and inspector

Clicking selects. The inspector exposes X, Y, width, height, opacity where relevant, lock,
show/hide where relevant, and reset. Numeric edits apply immediately; dragging updates the
fields immediately. Arrow keys nudge 1 px, Shift+arrow 10 px, and never while typing in an
input.

## Dragging and resizing

Pointer Events; correct under CSS scaling; no cumulative drift; a minimum size that prevents
inversion; positive width and height; clear handles in Edit Mode; the wheel's aspect preserved;
non-uniform resize for scenic boxes and the City; no browser-native drag.

## Z-order

Background, scenic art, wheel, figures, labels, City, City figures and counts, centre in-hand,
then overlays. Send Backward / Bring Forward at minimum for scenic art, so art can go behind or
in front of the wheel. Debug overlays never become part of exported layout data.

## Mirror / duplicate helpers

Mirror a selected scenic box or label horizontally across x=600 or vertically across y=600,
preserving dimensions. The layout is not forced to stay symmetrical.

## State persistence

`localStorage` so the layout survives refresh, plus Save Layout, Reset Layout, Export Layout
JSON and Import Layout JSON. The JSON carries true 1200 × 1200 coordinates and all editable
state: wheel, the eight art regions, image metadata where possible, labels, figure anchors and
counts, City geometry and player counts, in-hand geometry and count, visibility and guides.

Local images loaded through file inputs may not survive a session. Handle that gracefully. If
feasible, convert them to data URLs so exported JSON can recreate the layout — and if that
makes the JSON very large, offer an export without embedded image data.

## Copy Layout JSON

A dedicated button, producing data clean enough to use in the game code later, shaped roughly
like:

```json
{
  "version": 1,
  "canvas": { "width": 1200, "height": 1200 },
  "wheel": { "x": 210, "y": 180, "width": 780, "scale": 1.0 },
  "duties": {
    "clerical": {
      "art": { "x": 490, "y": 30, "width": 220, "height": 180 },
      "label": { "x": 520, "y": 200 },
      "figures": { "anchorX": 600, "anchorY": 280, "count": 3 }
    }
  },
  "city": { "x": 470, "y": 970, "width": 260, "height": 160, "players": [] },
  "inHand": { "visible": true, "x": 525, "y": 500, "width": 150, "height": 150, "count": 6 }
}
```

## Optional screenshot export

A PNG export of the 1200 × 1200 composition if it can be done cleanly without external
libraries. Layout JSON matters more.

## UI layout outside the stage

A scaled 1200 × 1200 stage, a side inspector, a compact top toolbar, dark neutral chrome, an
obvious Edit/Clean toggle, no unnecessary decoration. The inspector may scroll independently.
The stage keeps its square aspect.

## Usability

The selected object obvious in Edit Mode; concise labels; compact inputs; every control works;
no placeholder buttons; file loaders accept the relevant types; resize handles do not start a
stage drag; the display scale shown somewhere; a status line after save/import/export.

## Code quality

Readable: separated sections, comments on the coordinate-conversion and drag/resize code, no
huge minified strings, one central default-state object, centralised serialisation, validated
imports, safely clamped numbers, no `eval`, no network. The HTML works by double-clicking it.

## README

How to generate the HTML, how to open it, how to load the 32° wheel SVG, how Edit Mode and
Clean Preview work, how to export and import layout JSON, and where the generated HTML goes.

## Acceptance test

1. Generate HTML from the Python script.
2. Open HTML locally.
3. Stage is exactly 1200 × 1200 in internal coordinates.
4. Load an SVG wheel.
5. Scale and move wheel without changing its aspect ratio.
6. Move and resize each of eight art boxes.
7. Load at least one test image into an art box.
8. Put art partly behind the wheel.
9. Change a Duty occupancy from 0 to 4.
10. Move its figure anchor onto the intended wheel segment.
11. Set City counts for four players.
12. Show the in-hand pool with count 6.
13. Switch to Clean Preview and verify editing chrome disappears.
14. Return to Edit Mode.
15. Nudge a selected object with arrow keys.
16. Mirror one scenic box horizontally.
17. Export JSON.
18. Reset layout.
19. Import the exported JSON and restore the layout.
20. Refresh the page and verify saved state persists.

Implement the working tool, not a design proposal. Where something is ambiguous, choose a
sensible default and document it in the README rather than stopping for clarification.
