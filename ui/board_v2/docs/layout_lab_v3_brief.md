# Duty Wheel Layout Lab — V3 brief

Kept for the same reason as the first two: it records what was asked for, and what was
explicitly left to judgement. Where a decision was left open, the choice made and the reason
for it are written down in `layout_lab/README.md` under *Decisions the brief left open*.

This is the version that changed the layout concept rather than the dimensions.

---

Please update the existing **Duty Wheel Layout Lab** to the next version.

This update changes the underlying layout concept, not just some dimensions.

IMPORTANT:
- Work from the existing implementation.
- Preserve useful V2 functionality such as: wheel SVG loading, 32° aspect-ratio preservation,
  realistic acolyte sizing, Painted / Colored acolyte modes, City, In-Hand display, Undo / Redo,
  zoom, Clean Preview, Lab Session export/import, Game Layout export, black/game-dark
  backgrounds, wheel-relative anchors.
- Do not rebuild the tool from scratch unless necessary.
- Keep the implementation plain HTML/CSS/vanilla JavaScript generated by the existing Python
  script.
- No network dependencies.
- The HTML must continue to work by opening it locally.

## 1. Change the Duty module from 1200 × 1200 to 1400 × 1200

The fixed internal design coordinate system is now **1400 × 1200 px**.

The full-game target canvases remain 2039 × 1200 and 2283 × 1200, so the Duty module leaves
639 px beside it on the first and 883 px on the second.

The wheel itself should NOT automatically become wider just because the module is wider. The
extra horizontal space exists primarily to provide more room for compact Duty information while
sowing, and substantially larger Duty-action artwork after sowing.

Update all stage dimensions, centre calculations, horizontal mirror calculations, guides,
exports, boundary warnings, zoom calculations, PNG export, JSON validation and full-board-space
readouts to use 1400 × 1200.

### Migration from 1200 × 1200 V2 files

Support importing existing 1200 × 1200 V2 Lab Sessions where practical. When migrating an old
1200-wide layout into the new 1400-wide canvas: preserve Y coordinates, shift absolute X
coordinates by +100 px so the previous composition remains centred, preserve wheel-relative u/v
values, and recompute attached-object absolute positions from the migrated wheel.

Do not reject an otherwise valid V2 layout solely because its old canvas width is 1200.

## 2. New core design principle: two Duty-visual states

The UI no longer attempts to show 16 large scenic Duty-action images around the wheel
simultaneously. There are now TWO main presentation states: **SOW / PLANNING** and **DUTY ACTION
SELECTION**.

The same large wheel remains in the SAME position and at the SAME size in both states. Do not
animate or move the wheel between these states in the layout lab.

Add a prominent prototype-state selector `VIEW STATE` with options SOW / PLANNING and ACTION
SELECTION. The purpose is to compare these two compositions.

## 3. Revised overall 1400 × 1200 layout

Starting values, not hard constraints.

**Status / turn instruction** — dedicated area across the top, approximately x = 175, y = 20,
width = 1050, height = 95.

**Wheel** — initial target width ≈ 930–960 px; start at approximately x = 225, y = 355,
width = 950. Height should continue to come from the imported wheel asset's intrinsic 32° aspect
ratio; at the default ~0.53 ratio this gives roughly 950 × 503 px. Do NOT non-uniformly scale the
wheel. The wheel should remain centred horizontally.

**City** — centred beneath the wheel, suggested x ≈ 480, y ≈ 990, width ≈ 440, height ≈ 160. The
City remains separate from the Duty Wheel, not a ninth Duty, and aggregated as one representative
acolyte + count per player.

**No scenic Duty art above or below the wheel.** This is a deliberate design constraint. Do NOT
place the large scenic Duty-action artwork above the wheel, below the wheel, or in a radial halo.
The upper area is reserved primarily for turn/status information; the lower area for the City and
compact contextual controls such as Tithe. The scenic Duty artwork should appear LEFT and RIGHT of
the wheel only during Action Selection.

## 4. Dedicated turn status / instruction area

Add a new editable object, **Turn Status Area**: a permanent reserved area above the wheel,
draggable, resizable, lockable, visible/hidden, represented in Clean Preview and exported as
production geometry. Initial size approximately 1050 × 95 px.

It should support TWO text levels — an optional small context / phase line, and a primary
instruction line. For example: `SOW` / `Pick up Acolytes or Hire Buildings`, or `CLERICAL` /
`Select a Duty Action or take Tithe`.

Controls should include context text, main text, context show/hide, context font size, main font
size, horizontal alignment (left / centre / right), an optional player-turn accent, an accent
colour, and opacity if useful.

Default styling should be restrained: no large parchment panel, no bulky frame, text against the
dark background, perhaps a subtle divider or very faint backing only. The main instruction should
visually dominate the context line. Suggested default sizes in design coordinates: context text
≈ 16–20 px, main instruction ≈ 30–36 px.

### Status presets

1. `TURN` / `Pick up Acolytes or Hire Buildings`
2. `SOW` / `Choose the next Duty — 4 Acolytes remaining`
3. `CLERICAL` / `Select a Duty Action or take Tithe`
4. `ORDINATION` / `Choose an Acolyte to send on a Mission`
5. Custom

Allow all text to remain editable after applying a preset.

## 5. SOW / planning state

During sowing, the player needs to understand what the eight Duties can do, but does NOT need
sixteen large scenic illustrations. The wheel should dominate this state.

Show: the large wheel, realistic acolytes standing on it, the In-Hand counter in its centre, the
City below, four compact Duty summaries on the LEFT and four on the RIGHT. Do NOT show the large
scenic action artwork in this state.

## 6. Four compact Duty summaries on each side

Add one compact summary object per Duty, eight total, forming two vertical information banks
beside the wheel. A useful starting placement: LEFT x ≈ 15–25, width ≈ 200–215; RIGHT x ≈
1170–1185, width ≈ 200–215; four rows approximately between y ≈ 300 and y ≈ 820. Exact spacing
should be editable.

Suggested default distribution — LEFT top to bottom: Allocation, Ordination, Give Alms, Construct.
RIGHT top to bottom: Clerical, Taxation, Produce, Build Roads. But make every compact Duty summary
independently draggable so this distribution can later be changed, and do not hard-code layout
logic that depends on this exact mapping.

## 7. Compact Duty summary content

Each should show the Duty name, an Action A wax-seal icon, short Action A text, an Action B
wax-seal icon, short Action B text, and optionally a Tithe resource/icon if useful. The purpose is
planning information, not scenic illustration.

### Wax-seal icon support

Each Duty action should now have an action name, a short planning label, and an optional wax-seal
icon asset. Allow loading a local transparent PNG/WebP/SVG wax-seal icon for each action. If no
icon is loaded, use a simple circular seal placeholder containing A or B. The compact summary
should remain readable without final art assets.

### Text editing

Expose short labels in the inspector. Do not assume the final game action wording yet. Allow labels
to wrap to two lines if necessary.

## 8. Optional subtle Duty-to-wheel association

Because all compact summaries now sit on the left/right rather than exactly radially outside their
wheel space, optionally support a restrained association cue. Add a global option `Duty connectors`
with options OFF and subtle line, defaulting to OFF. If enabled, draw a thin unobtrusive line from
the compact Duty summary toward its corresponding figure/Duty anchor on the wheel. This must NOT
look like a large directional arrow. It is only an association cue, and must not be essential for
understanding the UI.

## 9. In-Hand display during sowing

Preserve the existing In-Hand concept in the wheel centre. During SOW / PLANNING: visible by
default, representative acolyte, remaining count, supporting `×6` and `6 LEFT`. It remains
wheel-relative. It is acceptable for the status text to be slightly redundant with the central
display, because the central display provides immediate spatial feedback.

## 10. Action selection state

After sowing completes, the interface changes presentation. The wheel must remain at the same X,
Y, width and height. Do NOT shift it to make room for the action artwork.

The currently selected Duty is highlighted. All compact Duty summaries should either disappear or
become strongly dimmed. Add a global prototype setting `Other Duty summaries` with options Hidden,
15% opacity and 30% opacity, defaulting to Hidden.

## 11. Selected Duty control

Add a prototype control `Selected Duty` — a dropdown of the eight duties, defaulting to Clerical.
Changing it should update the header context if automatic status mode is enabled, highlight the
corresponding Duty on or near the wheel, show that Duty's Action A image in the LEFT expanded-action
slot and its Action B image in the RIGHT slot, update action labels, and update optional Tithe
information. This is simulation only; no real gameplay engine is required.

## 12. Large expanded action art — left and right only

Do NOT position all 16 scenic action images independently around the wheel in Action Selection
state. Instead create TWO global display slots: **Expanded Action Left** and **Expanded Action
Right**. The selected Duty supplies its Action A and Action B assets to these slots, with LEFT =
Action A and RIGHT = Action B by default.

Suggested starting geometry — LEFT: x ≈ 10–30, y ≈ 360–390, width ≈ 360–390, height ≈ 340–380.
RIGHT: x ≈ 1010–1030, y ≈ 360–390, width ≈ 360–390, height ≈ 340–380.

These large artwork slots are ALLOWED to overlap behind the left and right edges of the wheel.
That overlap is intentional: with the wheel starting around x = 225, a 380 px-wide left image
starting at x = 20 extends to x = 400, so approximately 175 px can visually overlap and fade behind
the wheel. Likewise on the right.

### Artwork layering

Allow each expanded action slot to choose Behind Wheel or In Front of Wheel, defaulting to Behind
Wheel. The images are expected to fade into black around their edges. This should let the artwork
visually merge with the composition instead of looking like rectangular cards.

### Expanded action labels

Each expanded art choice should show the action name — `GAIN PIETY` above its artwork, `GAIN COINS`
above the other. Allow label X/Y, font size, show/hide and alignment.

The artwork itself should be treated as the clickable region in the eventual game, but this layout
lab does not need to perform gameplay actions. Add a visual "clickable preview" hover state if easy
— a very subtle brightness increase, a subtle border or glow. Do not make this flashy.

## 13. Action asset model

Separate the ACTION ASSET from its DISPLAY GEOMETRY. Each Duty action should store a name, a
shortLabel, a waxSealImage, a scenicImage and imageName metadata — but its large scenic artwork
should NOT need its own permanent x/y box. Instead the currently selected Duty's two scenic assets
are rendered into the global Left and Right Expanded Action slots.

This is an important architectural change. It prevents sixteen separate large-art geometries from
cluttering the production layout model.

## 14. Tithe treatment

In ACTION SELECTION state the player can choose Duty Action A, Duty Action B, or Take Tithe. Tithe
does NOT need a large scenic illustration. Create one compact Tithe choice, preferably beneath the
wheel, between the wheel and City if sufficient space exists. Suggested treatment: a Tithe
resource/seal above `TAKE TITHE`. Keep it compact, and let it be moved elsewhere if necessary.

It should support X/Y, width/height, visible, label, an optional resource/seal image, optional short
resource text, and lock/unlock. Do not force it into the wheel centre, and do not treat it as a
third large art card.

## 15. City

Keep the existing City design: below the wheel, not a Duty, no Duty actions, no Tithe, never
visited by the merchant, able to contain many acolytes, using one representative acolyte + count per
player. Preserve the optional City background image, Painted / Colored representative acolytes,
independent City scaling, counts, visibility, and position/size editing. The City must not expand
merely because counts increase.

## 16. Wheel visual emphasis

The wheel is the dominant object in SOW / PLANNING state. Add a simple selected-Duty highlight
simulation for ACTION SELECTION state. Because the final SVG geometry may not expose individual
segment DOM elements, do NOT assume the tool can recolor a real SVG segment internally. Instead
provide a movable highlight placeholder for each Duty anchor, or another lightweight overlay — a
soft elliptical glow, a thin ring, a small halo beneath figures. The purpose is simply to judge
whether the selected Duty can be made obvious. Do not modify the imported wheel asset.

## 17. Acolytes

Preserve all existing V2 acolyte functionality. The global Acolyte Height range remains 90–210 px.
Preserve the slider, the numeric field, Painted / Colored mode, one asset per player, player
colours, occupancy 0–4, mixed-player assignments, row / compact / shallow arc arrangements, the
City percentage and the In-Hand percentage. Use approximately 120 px as the default test height.

## 18. Clean Preview

Clean Preview must accurately represent the selected VIEW STATE.

**SOW / PLANNING** — show the Turn Status, the compact 4-left / 4-right Duty summaries, the wax
seal icons, the wheel, the duty acolytes, the In-Hand display and the City. Hide the expanded
scenic artwork, the Tithe action-selection control and editor chrome.

**ACTION SELECTION** — show the Turn Status, the selected Duty highlight, the large Action A
artwork on the left, the large Action B artwork on the right, the action labels, the wheel, the
existing figures, the compact Tithe choice, the City, and optionally dimmed compact summaries
depending on the selected setting. Hide the In-Hand display by default because sowing is complete,
and hide editor chrome. Provide an override to show In-Hand for debugging.

## 19. Edit Mode should make both states easy to compose

When in Edit Mode, preserve the currently selected view state. It should be possible to switch
between SOW / PLANNING and ACTION SELECTION without losing any geometry. Objects that are not
active in the current state may be hidden from the stage, but must remain editable from the side
panel if necessary.

Add concise inspector sections: LAYOUT, STATUS, SOW DUTY SUMMARIES, EXPANDED ACTIONS, TITHE,
ACOLYTES, CITY, VIEW. Avoid making the side panel overwhelming; collapsible sections are acceptable.

## 20. Default action names for prototyping

- CLERICAL — Gain Piety, Gain Coins
- ALLOCATION — Relocate Acolytes, Special Activity
- BUILD ROADS — Build Road, Build Shrine
- ORDINATION — Ordain, Send on Mission
- GIVE ALMS — Give Alms, Donate Building
- PRODUCE — Gain Wheat, Gain Stone
- CONSTRUCT — Construct Building, Construct Road
- TAXATION — use temporary labels: Action A, Action B

All labels must remain editable. Do not invent final Taxation wording.

## 21. Default SOW view

Status context `SOW`, main `Pick up Acolytes or Hire Buildings`. Wheel ~950 px wide, centred
horizontally, around y = 355. Acolyte height 120 px. Duty occupancy: Clerical 4, Allocation 3,
Build Roads 2, Ordination 1, Give Alms 4, Produce 2, Taxation 3, Construct 1, with mixed player
colours on Clerical. In Hand visible, Player 1, ×6. City: Player 1 ×7, Player 2 ×4, Player 3 ×2,
Player 4 ×5. Compact Duty summaries four left and four right. No large scenic art visible.

## 22. Default action-selection view

Selected Duty Clerical. Status context `CLERICAL`, main `Select a Duty Action or take Tithe`.
Expanded Left `Gain Piety`, Expanded Right `Gain Coins`. If Clerical scenic artwork has not been
loaded, show a large tasteful placeholder — `GAIN PIETY` / `scenic artwork` and `GAIN COINS` /
`scenic artwork`. Tithe visible, compact, below the wheel. In-Hand hidden. Other Duty summaries
hidden. Wheel and City at exactly the same geometry as the SOW state.

## 23. Optional state-comparison helper

Add a keyboard shortcut if straightforward: `1` = SOW / PLANNING, `2` = ACTION SELECTION. Do not
trigger these shortcuts while typing in an input. This should make it easy to flip rapidly between
the two designs while evaluating the composition.

## 24. Update the Game Layout export

Production-oriented Game Layout JSON at `"version": 3`, with `canvas` 1400 × 1200 and blocks for
`status`, `wheel`, `duties` (each with a `summary` box, `actionA` and `actionB` carrying `name` and
`shortLabel`, a `label` and `figures`), `expandedActions` (`left` and `right`, each with geometry
and a `layer` such as `behind-wheel`), `tithe`, `city`, `inHand` and `acolytes`.

Do not include the current Selected Duty, the current test occupancy, the current View State,
guides, zoom, undo history, editor selection, or the status preset currently chosen, unless these
are genuinely required as layout geometry. The Lab Session should preserve all prototype/editor
state.

## 25. Important design constraints

Please implement these explicitly rather than drifting back toward the previous radial-art design.

1. The module is **1400 × 1200**.
2. The wheel should remain large, roughly **930–960 px wide** initially.
3. The wheel does NOT change geometry between SOW and ACTION states.
4. Large scenic Duty artwork exists only in ACTION SELECTION state.
5. Only TWO large scenic images are shown at once: Action A left and Action B right.
6. Large scenic art is NOT placed above or below the wheel.
7. During SOW, all eight Duties are represented by compact readable summaries using wax-seal icons
   and short text.
8. Four compact Duty summaries are on the left and four on the right.
9. The Turn Status area is above the wheel.
10. The City remains below the wheel.
11. The In-Hand count appears in the wheel centre while sowing.
12. Tithe remains a compact third option rather than receiving another large scenic image.
13. Large left/right action art may overlap and fade behind the wheel.
14. Do not design the rest of the full game board yet.
