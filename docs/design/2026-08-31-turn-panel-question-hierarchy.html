The turn panel as a set of questions

Left column is the panel exactly as it renders today; right column is the proposal. Same width (428px, the real one), same states, same sentences. Every label, reason, note and number below was lifted from play_server running scenarios/bank_hire_market_ordination_001.json, driven through lift → duty → Action → one serf → hire → pay. Nothing is composed in the page and no control has been invented.

What the payload already carries

Every step carries its own prompt. After one serf is moved, the four surviving candidates split by their next unanswered step:

ordain=1 → combination 'none' and 'bank:market' — prompt “Hire the Bank … for 1 silver?”
ordain=2 and ordain=1,mission=1 — prompt “Move serfs and acolytes, up to 2 in total.”

Both sentences are printed into the panel as .turn-prompt rows. show() marks one offered and the other keeps display:none, so two questions’ answers appear under one question’s heading. The grouping is not missing — it is switched off.

ordination_next_move_consequence is written by the server onto the two combination steps, not the ordination ones. In the flat key row it lands last and reads as a caption on the acolyte button. It belongs to the hire answers.

Red holds 1 wheat, 2 silver, 0 stone. Village 2, Abbey 0. Duty value 2. The Bank is in the market; hiring costs 1 silver.

The grammar

§

Four things, four treatments

An open question.

Why not, from the payload.

Open. Seat-coloured rule, bright heading, parchment answers. Parchment means one thing only: a pressable answer to a question that is open now.

A question that has closed.

Closed. Rule goes grey, heading dims, answers become outlines. Present, unpressable, and visibly finished — absent would read as a broken page.

Answered somewhere else.→

Cost 2 · paid 1

Off-panel. No offered step of this question has a key in the panel, so the client already knows it is answered on the board. A glyph, not a sentence.

Controls. Never parchment unless they are answering an open question. Confirm is permanently the wider of the pair and is the only control that ever goes bright.

The rule that makes the rest fall out: a question is a visual object — heading plus its own answers, bound by a rule down the left. More than one can be open. A question’s heading sits where its answers sit, which is what puts the “Action or Tithe.” heading above the control rows in state 1 and leaves the payment heading pointing at the board in states 4–6.

Four sizes instead of one

Round 3 - 0 of 4 turns played   /   Sow 11px — context. Round line and phase column. Never competes.
No acolyte in the Abbey. 12px — annotation. Reasons and notes, always dimmer than what they explain.
Move serfs and acolytes, up to 2 in total. 13px bold — a question.
Move a serf from the Village to the Abbey 13.5px — an answer. The thing you press is the largest interactive text.

Today the round line, the phase rows, the prompt, every key, every control, the reason and the cost line are all 12–13px. The prompt is the only differentiated element and it is differentiated by #B7382E, the seat colour, which on #101010 is both the lowest-contrast text in the panel and the web’s standard colour for an error. The proposal moves seat identity into a 2px rule and sets the heading in ink.

Where the work lands

No new server copy. Every string above already exists: the two prompts are step.prompt, the reason is status.reason, the note is step.ordination_next_move_consequence, the gold sentence is the hire fact, and Cost n · paid n is already composed in the client at play_view_turn.js:2183 from two numbers it holds. The pips are those same two numbers, not a re-reading of a server sentence.

The change in show() is the point. Today it picks one prompt: every .turn-prompt is set unoffered and one is set offered. The proposal groups the offered steps by their own prompt and emits one block per distinct prompt, ordered by the step’s index in the candidate. That makes simultaneous questions the normal case rather than the exception, which is the part that keeps this from drifting the next time two steps overlap: nothing in the renderer or the client needs to know that this overlap is the hired-Bank one.

Ordering is derived, not chosen. Move before hire because the ordination step is index 4 and the combination step is index 5 in every surviving candidate. Today’s order is the reverse, and it is an accident of render order — _combination_keys is emitted before _ordination_keys and the flat flex-wrap keeps that order. State 3b shows the alternative so the choice is on the record rather than implied.

The closed-question state is new and needs a source. In states 4–6 the move question is drawn closed. The client can tell: the ordination keys are painted from ordinationPaymentStarted already, which is exactly “that question is over”. No engine change; it is the same flag, spent on the block instead of the buttons.

It is taller, and here is by how much. Measured off this page at 428px: state 1 206→225px, state 2 298→314, state 3 356→440, states 4–5 343→390, state 6 298→347. The 84px in state 3 is the price of printing the second question’s heading instead of hiding it, and it is the one increase I would defend without trimming. The rest is block spacing and can come down if the column is tight.

What is not settled. The prompt sentences keep their “Red:” prefix, which is now doubled by the seat-coloured rule. Removing it is a server change and not mine to make here. And a question whose answers are off-panel is marked with a glyph; if that proves too quiet in play, the honest fix is a server-written sentence, not a page-composed one.
